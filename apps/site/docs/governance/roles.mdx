Four roles, a fixed hierarchy. Everything above a tier also satisfies it.

| Role | Operational reads | Mutations | The sensitive reads |
| --- | --- | --- | --- |
| `owner` | yes | yes | yes — the only role that may act on an owner, or mint one |
| `admin` | yes | yes | yes — but never an owner's |
| `support` | yes | **no** | **no** |
| `employee` | no | no | their own account and their own data only |

**Operational reads** are the roster, usage totals, teams, plans, gate state and the audit log.
**The sensitive reads** are a person's synced settings and their conversation transcripts — the two
things that expose an employee's actual work. Support is the view-only tier for *operations*, not a
licence to read the company's words.

The role travels on the access token and `/v1/me` returns it, so the client knows whether to render
admin controls. **That is presentation only.**

## The rule table

Authorization is one table (`src/lib/permissions.ts`) with two axes, because the real rules have two:

- **`tier`** — the minimum standing to attempt the action at all.
- **`ownerSafe`** — whether it may be aimed at an owner by someone who is not one. False for
  everything that reads or changes a *person*, so "only an owner may act on an owner" is stated once
  rather than remembered at nine call sites.

Every handler asks `can(actor, action, target)` and the answer comes from that one place. Two
constraints sit beside it: minting or promoting to `owner` requires being one, and **changing your
own role or status is refused for everyone, owner included** — the last owner demoting themselves
leaves an organization nobody can administer.

<Note>
There is no separate admin web console. The admin UI lives inside the admin's own desktop client and
on the phone, against the same API any client uses. Hiding a button is not a control.
</Note>

## Adding a person

An invite creates the account with **no usable password** and emails a 6-digit activation code to
the address itself, good for 7 days. Nothing comes back to you to pass along by hand, and the
address is proven by the fact that the person could read it.

| Action | Endpoint | Who |
| --- | --- | --- |
| Invite | `POST /admin/users` | owner, admin |
| Re-send the invite code | `POST /admin/users/:id/activation` | owner, admin |
| List / read | `GET /admin/users`, `GET /admin/users/:id` | + support |
| The whole roster, with spend | `GET /admin/roster` | + support |
| One person, in one call | `GET /admin/users/:id/overview` | + support |
| Update role, status, profile, team | `PATCH /admin/users/:id` | owner, admin |
| Reset password (the mail-is-broken path) | `POST /admin/users/:id/reset-password` | owner, admin |
| Clear a device PIN | `POST /admin/users/:id/clear-pin` | owner, admin |
| Revoke every session | `POST /admin/users/:id/revoke-sessions` | owner, admin |
| Their audit trail | `GET /admin/users/:id/audit` | + support |

Re-sending an invite mints a fresh code and kills the old one, so a forwarded copy of the first email
stops working. Only an account still at status `invited` has an invite to re-send; anything else
answers `already_active`, and the way back in is a password reset.

Suspending an account and revoking its sessions are **separate acts** — suspension stops future
sign-ins, revocation kills the sessions that already exist. Offboarding is both.

## Policy, plans and teams

| Action | Endpoint |
| --- | --- |
| A person's allowlist and daily caps | `PUT /admin/users/:id/policy` |
| A person's monthly token plan | `PUT /admin/users/:id/plan` |
| The plan catalogue and its ceilings | `GET /admin/plans` |
| The organization's defaults | `PATCH /admin/org` |
| The organization by team | `GET /admin/teams` |

A user's effective policy is their own row where it has a value, falling back to the org row. Edits
land on devices within the edge cache window — about a minute — because an admin mutation deletes
the cached copy in KV. See [Quotas & enforcement](/governance/quotas).

Beyond spend, two controls decide what the agent *does*: the config overlay and capability grants.
Both are [Organization controls](/governance/org-controls).

## The sensitive reads

These are the two places an admin sees an employee's actual work. Each is admin-tier, blocked for
support, blocked against an owner unless the reader is one, and **each writes an audit row**.

### Repairing a user's settings

The support path for "my app is misbehaving", because the synced config row **is** the user's
desktop settings:

- `GET /admin/users/:id/config` reads it verbatim, and the disclosure itself is audited — the row
  carries the user's stored integration secrets.
- `PUT /admin/users/:id/config` writes it, or resets it with `{"config": {}}`. The fresh server stamp
  this mints is what makes it land: the desktop adopts any row stamped by someone else before it
  would re-push its own copy, so an admin's fix survives the user's next launch instead of dying
  under a stale client blob. Audited by **size only** — the content is the user's secrets and stays
  out of the log.

### Reading a transcript

`GET /admin/users/:id/conversations` lists a person's conversations; `/admin/conversations/:id/records`
opens one, merging the R2 archive with any live rows under one cursor; `/admin/conversations/:id/files/:sha256`
fetches an attachment, or the body of a message too large to ride in its own record.

The index already knows which surface each conversation came from and how many tool calls it ran,
without opening any of them — so "which conversations came from the phone" needs no disclosure at all.

## The organization row

`GET` / `PATCH /admin/org` carries the defaults:

| Field | Meaning |
| --- | --- |
| `name` | Organization name — it appears in the emails people receive |
| `default_model` | What a user with no allowlist may call |
| `default_allowed_models` | The default allowlist |
| `user_daily_token_cap` | Tokens per employee per UTC day (0 = unlimited) |
| `org_monthly_token_cap` | Tokens for the whole org per UTC month (0 = unlimited) |
| `search_enabled` | The search lane's master switch |
| `user_daily_search_cap` | Searches per employee per UTC day |
| `org_monthly_search_cap` | Searches for the whole org per UTC month |

## Watching the system

| Endpoint | What it answers |
| --- | --- |
| `GET /admin/usage` | Totals per user, from the daily rollup |
| `GET /admin/teams` | The same totals, grouped by team |
| `GET /admin/gates` | Live gate state — queue depth, in-flight per host, cooldowns, what each host served |
| `GET /admin/audit` | The audit log |
| `POST /admin/maintenance/run` | Run the nightly jobs now |

## Every mutation is audited

There is no admin action that does not leave a row, and two *reads* leave one as well. See
[Usage & audit](/governance/audit) for the full list and what each row carries.
