This is an enterprise agent platform built on one inversion:

**The agent runs on the employee's machine. The organization's API holds the truth.**

Nothing about the agent moves to a server. The employee's desktop app thinks, reads files, runs
commands and drives their browser locally, with the permissions that person already has. What moves
to the edge is the *record* — every model call, every conversation, every file, every setting, every
quota decision — through one Cloudflare Worker the organization owns.

The folder on disk (`~/.wfc`) is a cache. Delete it, sign in on any machine, and the workspace walks
back out of the organization.

## The two tiers

| | Where it runs | What lives there |
| --- | --- | --- |
| **Tier 1 — the agent** | The employee's device | The 15-region brain, capabilities, the markdown workspace, files, tool execution, the browser extension. `~/.wfc` is workbench and cache. |
| **Tier 2 — the master** | Cloudflare's edge | One Worker: auth, the model lane, the search lane, sync ingest, the capability registry, the admin layer. D1 is the relational master, R2 holds blobs and archives, KV caches config and session kill-markers, three Durable Objects hold the admission gates and the desktop↔phone link. |

Read [Architecture](/introduction/architecture) for the full map of what runs where.

## Four surfaces, one account

The employee sees the same account from four places, and they are not four agents:

- **Desktop** — where the agent actually runs. Everything else is a view of it.
- **Phone** — a paired device of the same organization account. It reads the record from the API
  and reaches a *running* desktop for live turns over the API's per-user bridge.
- **Browser extension** — the agent's hands in the employee's own Chrome. It talks to the desktop
  over `localhost` only; it has no cloud endpoint of its own.
- **Terminal** — `wfc`, a full client that attaches to the running desktop over the local socket.
  No window needed, which is what lets the agent run on a server reached over SSH.

[Where you can work from](/using/surfaces) compares them; [Sync](/sync/overview) explains exactly
what travels between them.

## What an employee actually gets

One agent that can read and write files, run commands, drive their real browser and their screen,
search the web, build documents, PDFs, spreadsheets and charts, transcribe and speak — **35
capabilities**, published from the organization's registry and mirrored onto every desktop.

Around that: projects and procedures so work is not retyped, automations that run on a schedule, a
memory that is edited rather than accumulated, and a plan-first stance for anything that would
change something. See [Working with the agent](/using/agent).

## What this edition does not have

This is a deliberately narrowed fork of a personal agent product. If you are coming from that
edition or from older documentation, these are gone:

| Removed | Why |
| --- | --- |
| Per-user model providers (OpenAI, Anthropic, OpenRouter, Ollama, Qwen, Kimi, MiMo, MiniMax, xAI, Stepfun, Z.ai) | The organization runs **one** model lane. A device cannot hold a provider key. |
| Telegram and WhatsApp channels | The channels are the app, the phone, the terminal and the browser extension. |
| Notion, GitHub, Google Workspace, Memes integrations | Replaced by first-class integrations built per deployment, not a connector menu. |
| Video generation | Removed from the API, every client and the capability registry. |
| The server-side `episodes` table | Dropped in migration `0011`. The agent still keeps its daily episode log **on the device**, where it feeds the nightly consolidation into knowledge; it just has no record of its own at the organization, and travels as an ordinary workspace file. |

What survives as an organization-provided service: **web search** (behind the API), **computer
use**, **speech-to-text** and **text-to-speech**. Everything else an agent can do comes from the
[capability registry](/sync/capabilities), published from the repository's `capabilities/` folder.
