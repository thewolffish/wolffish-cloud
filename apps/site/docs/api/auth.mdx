Sign-in is invite-only. There is no self-registration endpoint and no bootstrap route: an admin
creates the account, the platform emails a code to the person themselves, and they set the only
password that will ever exist on it.

## Activation — how an account is opened

`POST /admin/users` creates the row with **no usable password**: a random one nobody holds. The only
way in is a 6-digit code emailed to the address on the account.

| | |
| --- | --- |
| Lifetime | **7 days** |
| Wrong guesses | 10, then the code is burnt |
| Re-send | `POST /admin/users/:id/activation` (admins) or `POST /auth/activate/request` (the person) — either mints a fresh code and kills the old one |
| Redeem | `POST /auth/activate/confirm` with email, code and the new password |

The row is deleted **before** the password is written, so a code can never mint a second one. Only an
account still at status `invited` has anything to activate; anything else answers `already_active`
and the way back in is a reset.

<Note>
Nothing about the account ever travels to the admin. The code goes to the address itself, which is
also what makes the address proven. The one exception is a deployment with no mail configured at all
(`RESEND_API_KEY` unset — a local `wrangler dev`), where the invite response carries the code so the
API can still onboard someone. A configured deployment whose send *fails* gets the failure, never
the code.
</Note>

## Passwords

PBKDF2-SHA256, 100,000 iterations, a 16-byte per-user salt.

Self-service reset is a code emailed the same way: `POST /auth/reset/request`, then
`/auth/reset/confirm`. It lives **10 minutes** and allows 5 wrong guesses.

The admin escape hatch, for when mail is broken, is `POST /admin/users/:id/reset-password` — it mints
a one-time temporary password with an expiry, and the next sign-in forces a personal one. A temp
password that has expired fails with `temp_password_expired`.

Activating an account by any route drops any pending invite code, so a stale invite can never set a
second password later.

## Tokens

Two tokens, deliberately asymmetric:

| | Access token | Refresh token |
| --- | --- | --- |
| Shape | HS256 JWT | `<session id>.<secret>` |
| Lifetime | **15 minutes** | 30 idle days |
| Stored server-side | Nothing — it is stateless | Only a SHA-256 hash of the secret |
| Sent on | Every request | Only `/auth/refresh` |

A refresh rotates: the presented secret is replaced by a new one. **A refresh secret that does not
match the current hash is treated as reuse** — possible theft — and the session is killed outright
rather than refreshed.

Both tokens are sealed with the OS keychain on the desktop and the OS keystore on the phone.

## Revocation

Because the access token is stateless, the only per-request storage read is one KV lookup for a
session kill-marker.

```text
revoke → write kill:<session id> to AUTH_KV   (visible globally within ~a minute)
       → delete the D1 session row            (authoritative on every refresh)
```

So a revoked session dies at the next request within KV propagation, and at absolute worst when the
15-minute access token expires. There is no path by which a revoked session survives longer than
that.

Four things revoke:

- The user signs out (`POST /v1/logout`).
- The user unpairs a device (`DELETE /v1/devices/:id`).
- An admin revokes every session (`POST /admin/users/:id/revoke-sessions`).
- An admin suspends or disables the account.

Revoking also closes that device's bridge socket on the spot and drops its push registration, so a
signed-out phone stops receiving immediately rather than at the next poll.

## The device PIN

A 4-digit PIN quick-locks the desktop app. It is **local-only**: never transmitted, never stored
server-side, and unreadable by an admin.

What an admin *can* do is ask for it to be cleared — `POST /admin/users/:id/clear-pin` sets a pending
clear-request, the client wipes its local lock, and `POST /v1/device/pin` acknowledges. The PIN
itself never enters the exchange.

## Pairing a phone

Pairing is how a phone becomes a signed-in device of the same user without ever seeing a password.

```text
desktop ── POST /v1/pair/offer ──▶ API      (code + QR token, 3 minutes, single-use)
phone   ── POST /auth/pair/claim ──▶ API    (whichever it saw)
                                    └──────▶ device row + session, minted atomically with the claim
```

The single-use guarantee is the `UPDATE` that marks the offer claimed — it can only ever succeed
once. Offers live in D1 rather than KV precisely for that: KV's eventual consistency could let one
code mint two sessions for up to a minute.

Only hashes are stored. The typed code is Crockford base32 with `I`, `L`, `O` and `U` removed so it
survives being read aloud, and the claim endpoint is rate-limited per IP because an 8-character code
is 40 bits behind a three-minute window.

## Roles on the token

The access token carries the role, and `/v1/me` returns it so the client knows whether to show admin
controls. That is a *rendering* decision only — every admin endpoint re-checks against the same rule
table. See [Roles & admin](/governance/roles).

## Rate limits

Every unauthenticated door is limited per email and per IP over a 15-minute window: login, activation
request, activation confirm, reset request, reset confirm and the pairing claim. A limited caller
gets `rate_limited`, never a hint about whether the account exists.

## Sessions and hygiene

The nightly run deletes `device_sessions` rows more than 30 days past expiry, expired password-reset
codes, and pairing offers older than a day. An activation row is not swept on a timer — it is
replaced on every re-send and deleted the moment a code is consumed or the account is activated by
any other route. See [Operate](/operations/operate).
