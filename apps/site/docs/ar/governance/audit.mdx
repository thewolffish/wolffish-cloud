سجلّان، يكتبهما شيئان مختلفان، لسؤالين مختلفين.

| السجل | من يكتبه | يجيب عن |
| --- | --- | --- |
| `usage` + `usage_daily` | المقياس، عند كل قرار على أي مسار | *كم أنفقت المنشأة، ومن أنفق؟* |
| `audit_log` | كل تعديل إداري | *من غيّر ماذا، ومتى؟* |

وكلاهما في قاعدة بيانات D1 الخاصة بالمنشأة. ولا يغادرها أي منهما.

## سجل الاستخدام

كل قرار على أي من المسارين — مسموح أو مرفوض أو خطأ — يصير **صفًا خامًا واحدًا وزيادةً واحدة في
التجميع اليومي، تُكتبان في دفعة D1 ذرّية واحدة**. فلا تعتمد الإجماليات أبدًا على نجاة الصفوف الخام
من مسح الاحتفاظ.

يحمل صف `usage` الخام:

| العمود | المعنى |
| --- | --- |
| `user_id`، `device_id` | من، وعلى أي جهاز |
| `surface` | أي واجهة أنفقت — `inapp`، `mobile`، `extension`، `heartbeat`، `procedure`، `api`؛ و`''` عند عدم النسبة |
| `kind` | `chat` أو `search` |
| `model`، `upstream` | أي نموذج، على أي مضيف |
| `tokens_in`، `tokens_out`، `tokens_cached` | أعداد دقيقة كما أبلغ المضيف؛ والمخزَّن جزء من الإدخال |
| `cost_microusd` | تكلفة المضيف المبلَّغة إن وُجدت، وإلا تسعير من أعداد الرموز |
| `latency_ms` | كم استغرق |
| `decision` | `allowed` · `denied_model` · `denied_quota` · `error` |
| `error` | سبب الفشل إن وُجد |
| `created_at` | بتوقيت UTC |

نسبة الواجهة مهمة لأن أدوار الهاتف تعمل على جهاز **سطح المكتب**: فبدونها لا يمكن تمييز إنفاق الهاتف
عن إنفاق التطبيق، ويصير إنفاق الإضافة غير مرئي.

### ما لا يُسجَّل عن قصد

- **لا محتوى طلب. ولا محتوى رد.** الموجّه لا يسجّل جسدًا ولا يخزّنه. ولا يقرأ من التدفّق إلا بقدر ما
  يجد كتلة الاستخدام.
- **لا نص استعلام بحث.** يسجّل الصف أن بحثًا جرى، لا ما سُئل.
- **لا هوية تُرسل إلى الأعلى.** الطلب الصادر هو جسد العميل مع معرّف النموذج السلكي ومفتاح المنشأة.

ومراقبة العامل بيانات وصفية فقط للسبب نفسه: الأخطاء، والزمن، والأحداث المهيكلة الخاصة بالمنصة.

### قراءته

| نقطة النهاية | من | ماذا |
| --- | --- | --- |
| `GET /v1/usage` | الموظف | سجله الخام |
| `GET /v1/usage/days` | الموظف | استخدامه مطويًا حسب اليوم |
| `GET /admin/usage` | owner, admin, support | إجماليات كل مستخدم من التجميع |

شاشة الاستخدام في سطح المكتب لا تمسك دفاترها: تُعاد بناؤها من `GET /v1/usage` بعد المحو وتُصالَح على
تطبيق يعمل، فتنضم استدعاءات أجهزة الموظف الأخرى وتعرض كل واجهة رقم المنشأة.

## سجل التدقيق

كل تعديل إداري يكتب صفًا واحدًا: الفاعل، والإجراء، والهدف، وكتلة تفاصيل JSON، وطابعًا زمنيًا. اقرأه
بـ `GET /admin/audit`.

| الإجراء | متى يُكتب |
| --- | --- |
| `user.invite` | إنشاء حساب وإرسال رمز تفعيله |
| `user.resend_activation` | إرسال رمز دعوة جديد، وقتل القديم |
| `user.read_activation_code` | قراءة مشرف لرمز تفعيل معلّق |
| `user.update` | تغيير دور أو حالة أو فريق أو ملف |
| `user.reset_password` | إصدار كلمة مرور مؤقتة |
| `user.read_reset_code` | قراءة مشرف لرمز استعادة معلّق |
| `user.revoke_sessions` | إبطال كل الجلسات |
| `device.clear_pin` | طلب مسح قفل محلي على جهاز |
| `policy.set` | تغيير قائمة مستخدم أو سقوفه |
| `plan.set` | تغيير خطة الرموز الشهرية لمستخدم |
| `config.view` | **قراءة** مشرف لإعدادات مستخدم |
| `config.set` | كتابتها أو إعادتها إلى الصفر |
| `conversation.view` | **قراءة** مشرف لأحد نصوص مستخدم |
| `org.update` | تغيير افتراضات المنشأة |
| `org.config_overlay` | مطالبة المنشأة بمسارات إعدادات أو إعادتها |
| `capability.put` · `capability.delete` | تغيير السجل |
| `capability.grants` | تغيير من تصل إليه القدرة |
| `maintenance.run` | تشغيل المهام الليلية يدويًا |

الفاعل عادةً شخص. أما كتابات القدرات القادمة عبر مسار النشر في التكامل المستمر فتُسجَّل باسم
`ci:publish`، لأن الخط يحمل مفتاح نشر لا جلسة.

### القراءتان المُدقَّقتان

`config.view` و`conversation.view` هما **القراءتان** المُدقَّقتان الوحيدتان في الواجهة. وكل ما عداهما
في الجدول تغيير. وهذا التفاوت هو المقصود: ذانك الصفّان هما أسرار تكاملات الشخص وكلامه الفعلي، وإفصاحٌ
لا يترك أثرًا ليس ضابطًا يستطيع أحد الإشارة إليه.

وكلاهما يُكتب **بالحجم أو بالإشارة، لا بالمحتوى**: `config.set` يسجّل حجم الكتلة،
و`org.config_overlay` يسجّل المسارات المُطالَب بها لا قيمها، وقراءة النص تسجّل أي محادثة فُتحت.
فالسجل يقرؤه عدد أكبر ممن يقرأ ما يصفه.

## الاحتفاظ

يحتفظ D1 بنافذة ساخنة محدودة، ويذهب الذيل الطويل إلى R2. وكل ذلك يجري في المهمة الليلية
(`17 3 * * *` بتوقيت UTC)، ولكل مهمة موعدها النهائي فيتصرّف التراكم عبر ليالٍ متتابعة بدل أن يتجاوز.

| البيانات | تبقى في D1 | ثم |
| --- | --- | --- |
| سجلات المحادثات | ١٤ يومًا بعد آخر لمسة | تُنقل إلى كتلة JSON مضغوطة في R2 (`archive/<user>/<conv>.json.gz`) وتُحذف الصفوف |
| صفوف `usage` الخام | ١٨٠ يومًا | تُصدَّر إلى R2 مضغوطة ثم تُحذف |
| تجميع `usage_daily` | بلا حد | وهو ما تقرأه إجماليات الإدارة |
| المحادثات المحذوفة | الشاهدة للأبد؛ والسجلات ٣٠ يومًا | تُمحى السجلات وكتلة الأرشيف — فـ«امحُ بياناتي» محوٌ حقيقي بعد شهر |
| الجلسات المنتهية | ٣٠ يومًا بعد الانتهاء | تُحذف |
| رموز الاستعادة | حتى الانتهاء | تُحذف |
| عروض الاقتران | يوم واحد | تُحذف — فالعرض باب لثلاث دقائق |
| الكتل اليتيمة | — | تُجمع ليليًا |

والأرشفة غير مرئية للعملاء: قراءة السجلات تدمج كتلة R2 مع أي صفوف وصلت بعدها، تحت عقد المؤشّر نفسه.
والمحادثة التي تعود إلى الحياة تراكم صفوفًا جديدة في D1 ببساطة، وتدمجها التمريرة الخاملة التالية.

## من أين تأتي الأرقام

`GET /admin/gates` هو العرض الحي — عمق الطابور، والجاري لكل مضيف، وفترات الراحة، وما خدمه كل مضيف.
يقرأ البوابات مباشرة لا السجل، فيجيب عن «ما يحدث الآن» لا عن «ما حدث».
